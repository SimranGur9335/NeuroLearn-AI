# Architectural Decision Record (ADR-001)

## Status
Approved

## Context
During the NeuroLearn AI production readiness audit, we identified a hybrid database mapping architecture in the Wellness module:
1. `backend/wellness_models.py` defined fully developed SQLAlchemy ORM declarative models.
2. `backend/wellness_crud.py` executed raw, parameterized SQL queries via `db.execute(text(...))` directly on the database engine.
3. No active controller, controller helper, or route handler imported or used the definitions in `wellness_models.py`.

Having two duplicate, conflicting database representations in the same feature module creates technical debt, confusion for future developers, and a hybrid architecture hazard.

## Decision
We formally standardize the Wellness module on **Raw SQL** database queries. 

As a consequence of this decision:
- We will deprecate and archive/remove the unused `backend/wellness_models.py` file to clean up the backend codebase.
- Future database expansions or modifications to the Wellness logs, focus sessions, statistics, and weekly reflections will continue to use standard parameterized SQL statements via SQLAlchemy's `db.execute(text(...))` queries.

## Rationale
1. **Consistency**: The startup migrations, attendance tracking registries, faculty analytics metrics, and dashboard summary views already standardise on Raw SQL. Standardizing Wellness on Raw SQL maintains consistency across the entire backend.
2. **Performance**: Parameterized raw SQL queries execute directly without ORM translation layer overhead, yielding slightly lower latency which is crucial for high-frequency checks like Pomodoro timers and focus sessions.
3. **Safety**: Transitioning the active CRUD logic in `wellness_crud.py` to ORM models would introduce high regression risk and potential bugs in the state engine (streak tracking, weekly reflections) right before production deployment.

## Consequences
- Unused declarative model file `wellness_models.py` is safely removed from the repository.
- Schema changes will continue to be managed through explicit SQL migration definitions on startup.
- Future database query extensions must follow the parameterized SQL convention.
